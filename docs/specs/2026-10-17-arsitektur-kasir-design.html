Spec Arsitektur Aplikasi Kasir Sembako

Desain v1.0 · 17 Oktober 2026 · Status: menunggu review · Dasar: PRD, laporan riset tech stack
Keputusan inti: satu kasir.exe (Go) berjalan sebagai Windows service di PC kasir, menyimpan data di SQLite lokal, dan menyajikan satu aplikasi React untuk layar kasir (Edge kiosk) dan HP pemilik (lewat Cloudflare Tunnel). Data dirancang append-only dengan UUIDv7, store_id, dan outbox, supaya fase cloud dan multi-cabang tinggal ditambahkan tanpa menulis ulang.

1. Konteks & kriteria

Yang sudah diputuskan

  • Satu toko, 1 meja kasir, aplikasi untuk toko sendiri (bukan SaaS). Multi-cabang mungkin nanti.
  • Kasir memakai PC/laptop Windows; perangkat belum dibeli.
  • Kasir harus tetap bisa jualan tanpa internet. Pemilik memantau dari HP. Struk dicetak di printer thermal.
  • Struk opsional per transaksi. Laci uang manual, tidak tersambung ke printer.
  • Dashboard pemilik cukup bisa diakses saat PC kasir menyala (opsi A); desain siap naik ke salinan cloud (opsi B).
  • Tidak ada timbangan tersambung; berat curah diinput manual.
  • Biaya: hosting Rp0; akses jarak jauh memakai domain murah (±Rp25.000/tahun untuk .my.id).

Kriteria keberhasilan teknis

  1. Tidak ada transaksi yang hilang atau tercatat dobel, termasuk saat listrik padam.
  2. Hasil scan muncul di keranjang < 300 ms; pencarian barang di server < 50 ms (p95) untuk 20.000 barang.
  3. Biaya operasional bulanan Rp0.
  4. Naik ke dashboard cloud dan multi-cabang tanpa migrasi skema besar.
  5. Bisa dirawat satu developer: satu bahasa backend, satu frontend, satu file yang di-deploy.

2. Arsitektur

PC Kasir (Windows 11, user "Kasir" non-admin, auto-login)
├─ kasir.exe  — Windows service, auto-restart saat crash, listen 127.0.0.1:8080
│   ├─ REST API (kontrak OpenAPI) + aturan bisnis
│   ├─ SQLite (WAL, synchronous=FULL) + tabel outbox_events
│   ├─ Penyusun ESC/POS → Windows print spooler (RAW)
│   ├─ Backup terjadwal (VACUUM INTO → folder lokal, flashdisk, R2)
│   └─ SPA React hasil build (go:embed)
├─ Edge mode kiosk → http://localhost:8080/kasir
├─ Scanner USB (mode keyboard/HID) · Printer thermal USB · Laci manual
└─ cloudflared (service) ──► Cloudflare Tunnel + Access (email pemilik)
                                   │
                    HP pemilik ────┘  https://kasir.<domain>.my.id/owner  (PWA)

Satu aplikasi web dengan dua bagian: /kasir (dioptimalkan keyboard, layar PC) dan /owner (mobile-first). Bundle dipisah per bagian.

Alternatif yang ditolak: cloud-first PWA (storage browser bisa dihapus dan browser tetap butuh agen lokal untuk printer), sync engine pihak ketiga (belum perlu untuk 1 kasir; konflik dihindari lewat model data), shell desktop Tauri/Electron (hanya pembungkus jendela; Wails v2 jadi cadangan bila butuh jendela native), Postgres di PC kasir (beban operasional tanpa manfaat untuk satu penulis).

4. Struktur kode

kasir-sembako/
├─ api/openapi.yaml          kontrak API (sumber kebenaran)
├─ server/
│  ├─ cmd/kasir/             main.go: wiring, perintah install/run/restore
│  └─ internal/
│     ├─ platform/           db, config, log, id (UUIDv7), clock, httpx, problem+json
│     ├─ catalog/            barang, satuan & konversi, harga grosir, kategori, pencarian
│     ├─ inventory/          ledger stok, barang masuk, opname, HPP rata-rata
│     ├─ sales/              transaksi, pembayaran, batal/retur
│     ├─ credit/             kasbon pelanggan
│     ├─ shift/              buka/tutup shift, kas keluar
│     ├─ auth/               user, PIN/password, session, peran
│     ├─ report/             read model: omzet, laba, stok menipis, kasbon
│     ├─ printing/           penyusun ESC/POS + wrapper winspool, antrean cetak ulang
│     ├─ outbox/             penulisan event (relay ke cloud di fase B)
│     ├─ backup/             snapshot, enkripsi, upload, restore
│     └─ web/                SPA hasil build (go:embed)
├─ web/                      React + Vite (routes /kasir dan /owner)
├─ scripts/                  install.ps1, update.ps1
├─ docs/                     PRD, riset, spec, rencana
└─ Taskfile.yml

Setiap paket fitur berisi domain.go (tipe dan aturan murni, tanpa DB), service.go (use case dan batas transaksi), repo.go (interface; implementasi SQLite dari sqlc) dan http.go (handler sesuai OpenAPI). sales memakai catalog, inventory, credit, shift lewat interface; report hanya membaca. Tidak ada dependensi melingkar. Interface repository memungkinkan implementasi Postgres untuk hub cloud tanpa menyentuh logika bisnis.

6. Alur bayar

1. Keranjang dibuat     → frontend membuat sale_id (UUIDv7); keranjang disimpan di localStorage
2. Kasir tekan Bayar    → POST /api/sales {sale_id, items, payments, print: true|false}
3. Server, SATU transaksi DB:
     cek shift terbuka → hitung ulang harga & total dari katalog
     → simpan sale + items + payments → stock_movements (+ credit_ledger bila kasbon)
     → update product_stock → outbox_events → activity_log (bila ada override PIN)
   COMMIT (synchronous=FULL)
4. Setelah commit       → bila print=true: kirim struk ke printer
5. Respons              → {sale, print_status: tercetak | tidak_dicetak | gagal}
  • Idempoten: sale_id yang sudah ada mengembalikan transaksi tersimpan, tidak membuat yang baru.
  • Server otoritatif: bila harga berubah sejak keranjang dibuat, server mengembalikan 409 PRICE_CHANGED dengan keranjang terbaru untuk dikonfirmasi kasir.
  • Struk opsional: pengaturan pemilik "Cetak struk otomatis" menentukan default; kasir bisa mengubahnya per transaksi (satu tombol/shortcut). Struk transaksi mana pun bisa dicetak ulang dari riwayat.
  • Cetak gagal ≠ penjualan gagal: penjualan tetap tersimpan, struk masuk antrean cetak ulang.

7. Penanganan error

KondisiPerilaku
Listrik padam saat bayarTransaksi DB atomik; keranjang pulih dari localStorage; sale_id sama mencegah dobel.
Kasbon melebihi limitDitolak (CREDIT_LIMIT), kecuali PIN pemilik; override dicatat.
Printer offline / kertas habisPesan ke kasir, struk ke antrean cetak ulang.
Service crashWindows service recovery me-restart; frontend menampilkan banner "Server tidak tersambung" dan mencoba ulang.
Jam PC mundurDibandingkan dengan transaksi terakhir; peringatan ke kasir dan pemilik.
Internet/tunnel matiKasir tidak terpengaruh; dashboard hanya tidak bisa diakses dari luar.
Edit harga bersamaan dengan transaksiPenulis tunggal SQLite menserialisasi; harga saat commit yang berlaku, plus 409 di atas.

Semua error API memakai application/problem+json (RFC 9457) dengan kode stabil (SHIFT_CLOSED, PRICE_CHANGED, CREDIT_LIMIT, PIN_REQUIRED, …). Frontend memetakan kode ke pesan Bahasa Indonesia.

8. Struk, scanner, laci

  • Struk: penyusun ESC/POS sendiri (±200 baris: ESC @, ESC a, ESC E, GS !, ESC t, GS V) + wrapper winspool (OpenPrinter → StartDocPrinter RAW → WritePrinter) lewat golang.org/x/sys/windows. Lebar kolom dikonfigurasi (32 untuk 58 mm, 48 untuk 80 mm). Antarmuka Printer punya implementasi file-sink untuk test dan e2e.
  • Scanner: mode keyboard (HID), diakhiri Enter + suffix khusus. Frontend memasang listener keydown global; burst dengan jeda < ~30 ms yang diakhiri Enter/suffix dianggap scan.
  • Laci: manual, tidak dikendalikan aplikasi. Kontrol kas lewat hitung uang fisik saat tutup shift dan laporan selisih. Laci otomatis bisa ditambah nanti (perintah ESC p) tanpa perubahan desain.

12. Build, CI, instalasi

  • task gen: oapi-codegen, orval, sqlc. Kode hasil generate di-commit; CI gagal bila ada drift.
  • task build: vite build → embed → CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build dengan versi di -ldflags.
  • Dev: Vite dev server mem-proxy /api ke go run.
  • CI (GitHub Actions): lint, test (Linux + Windows), e2e, artefak kasir.exe; tag rilis membuat GitHub Release.
  • Instalasi (install.ps1): exe ke C:\Program Files\Kasir, data ke C:\ProgramData\kasir; kasir.exe install mendaftarkan service + recovery; user Windows "Kasir" non-admin dengan auto-login dan Edge kiosk di startup; cloudflared sebagai service; konfigurasi nama printer & lebar kertas; nonaktifkan sleep dan atur jam aktif Windows Update.
  • Update (update.ps1): stop service → backup → ganti exe → start (migrasi jalan otomatis).

14. Fase berikutnya (di luar MVP)

  1. Fase B — dashboard cloud: relay outbox (goroutine + backoff) → POST /events di Go pada Cloud Run, Postgres Neon Free, UNIQUE pada event id; endpoint pull ber-cursor untuk master data (harga, barang) dari pusat ke toko.
  2. Multi-cabang: setiap toko menjadi spoke dengan pola yang sama.
  3. Installer Inno Setup, auto-update, struk WhatsApp, QRIS dinamis, laci otomatis bila dibutuhkan.
  4. Sync engine (PowerSync) hanya dipertimbangkan bila satu toko punya beberapa terminal yang sama-sama mengedit master data.

15. Risiko & validasi di prototipe

  • Domain .my.id bisa diarahkan ke nameserver Cloudflare dan tunnel berjalan.
  • Free tier Cloudflare Access masih mencakup kebutuhan (sumber resmi belum terbuka saat riset).
  • Printer yang dibeli: lebar kolom, code page, dan pemotong kertas sesuai perintah ESC/POS standar.
  • Edge kiosk + auto-login user non-admin berjalan stabil di Windows 11 setelah update.
  • PC kasir sebagai titik gagal tunggal: dimitigasi UPS, backup, dan prosedur restore yang sudah diuji.
  • Laci manual tanpa jejak buka-tutup: dimitigasi hitung kas tutup shift dan laporan selisih.
