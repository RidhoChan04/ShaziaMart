Laporan riset · 15 Oktober 2026 · sumber: research_notes/

Taruh Go dan SQLite di kasir, cloud menyusul

Rekomendasinya begini. Bangun satu binary Go yang jalan sebagai Windows service di PC kasir. Data disimpan di SQLite lokal (modernc.org/sqlite, mode WAL dengan synchronous=FULL). Binary yang sama menyajikan SPA React ke Edge mode kiosk di PC kasir dan ke browser HP pemilik. Struk dicetak dengan mengirim byte ESC/POS RAW ke Windows print spooler, dan laci uang dibuka dengan perintah ESC p ke printer yang sama. Skema data dirancang untuk hub-and-spoke sejak hari pertama. Penjualan dan mutasi stok bersifat append-only dengan UUIDv7 dan branch_id, ditambah tabel outbox yang nanti di-relay ke Postgres cloud gratis begitu cabang kedua atau dashboard cloud dibutuhkan. Pola ini sama dengan yang dipakai Loyverse, Square, Shopify, Toast, dan Odoo: penjualan disimpan dulu di perangkat, lalu diunggah sebagai antrean ketika koneksi kembali. Bedanya, penyimpanan lokal kita berupa file SQLite di disk, bukan storage browser yang secara default hanya "best effort". Untuk satu kasir belum perlu sync engine. PowerSync dan Turso Sync baru masuk akal jika ada beberapa terminal yang sama-sama bisa mengedit data, sementara Zero tidak bisa dipakai sama sekali karena menolak tulis saat terputus. Ada dua koreksi atas asumsi awal. Pertama, Tailscale Personal resmi hanya untuk penggunaan non-komersial. Kedua, Litestream di Windows berstatus "at your own risk". Karena itu, jalur akses jarak jauh yang Rp0 dan legal adalah Cloudflare Tunnel + Access, yang butuh domain berbayar tahunan, dan backup utamanya adalah VACUUM INTO terjadwal ke Cloudflare R2 free tier. Jadi "hosting Rp0" realistis, tapi "total Rp0" tidak. Biaya minimum yang jujur adalah satu domain per tahun.

Server lokal + outbox mengalahkan tiga arsitektur lain untuk satu toko

Ada empat kandidat arsitektur. Pertama, server lokal: binary Go + SQLite di PC kasir, UI diakses lewat browser. Kedua, desktop shell: Wails, Tauri, atau Electron dengan DB tertanam. Ketiga, sync engine local-first. Keempat, cloud-first: Postgres di cloud dengan PWA yang menyimpan antrean di IndexedDB. Keempatnya bisa dibuat jalan. Perbedaannya ada di jaminan offline dan beban operasional.

Kelemahan cloud-first ada di lapisan storage. Storage browser secara default "best effort" dan boleh dihapus browser tanpa memberi tahu pengguna. Chromium dan Firefox menghapus origin yang paling lama tidak dipakai lebih dulu ketika disk penuh (web.dev). WebKit pun mengabulkan navigator.storage.persist() hanya "based on heuristics", tanpa jaminan (WebKit). Di PC kasir dengan Chrome dan disk lega, eviction jarang terjadi. Tapi cukup satu kali "clear browsing data" atau reset profil, penjualan yang belum tersinkron hilang. Odoo, POS web paling matang yang diteliti, sampai harus menangani error "Connection to Indexed Database server lost" dengan dialog reload yang menyebut "unsaved orders" (Odoo indexed_db.js).

Masalah kedua cloud-first lebih menentukan: browser tidak bisa bicara langsung dengan printer thermal USB. Odoo butuh IoT Box atau program "Windows virtual IoT" untuk printer ESC/POS USB (Odoo IoT). NexoPOS memakai Nexo Print Server (NexoPOS). POS Awesome V15 memakai QZ Tray (POS-Awesome-V15). Kalau sebuah agen lokal tetap harus dipasang demi printer dan laci, lebih masuk akal agen itu juga yang memegang data. Dengan begitu cloud-first kehilangan keunggulan utamanya, yaitu tidak perlu instal apa pun.

Sync engine sudah matang di 2026, tapi kecocokannya dengan kasus ini berbeda-beda. PowerSync paling relevan untuk POS. Penulisan dari klien masuk ke upload queue FIFO yang blocking ke backend API milik kita sendiri, jadi Go tetap jadi validator otoritatif untuk uang dan stok (PowerSync consistency). Free tier-nya $0 dengan batas 2 GB sync per bulan dan 50 klien bersamaan. Ada catatannya: proyek free dinonaktifkan setelah tidak aktif, dan halaman yang sama menyebut dua angka berbeda untuk ini, 1 minggu dan >2 minggu (PowerSync pricing). SDK .NET untuk Windows masih beta, dan tidak ada SDK klien Go (PowerSync SDK). Turso Sync satu-satunya yang punya klien Go, tapi resolusi konfliknya "last push wins" (Turso Sync). Itu berbahaya untuk kolom stok yang mutable. ElectricSQL tegas menulis "Electric does not do write-path sync" (Electric). Zero hanya mengizinkan baca saat disconnected (Zero), jadi gugur untuk syarat "tetap jualan tanpa internet". Pasar vendornya juga sedang berubah: Supabase mengakuisisi Turso (diumumkan 2 Oktober 2026) (PR Newswire via Webull) setelah sebelumnya meng-acqui-hire tim Triplit (Supabase). Mengikat data kasir ke engine yang roadmap-nya belum jelas adalah risiko yang tidak perlu diambil.

Outbox buatan sendiri ternyata kecil. Polanya: pesan ditulis ke tabel outbox dalam transaksi DB yang sama dengan penjualan, sehingga pesan "guaranteed to be sent if and only if the database transaction commits". Relay-nya bisa mengirim lebih dari sekali, jadi konsumen harus idempotent (microservices.io). Implementasinya cukup goroutine relay dengan backoff, endpoint POST /events di cloud dengan UNIQUE pada event UUID, dan satu endpoint pull ber-cursor untuk master data (produk, harga) dari pusat ke toko, mirip model checkpoint RxDB (RxDB). Bagian paling sulit dari sync, yaitu konflik pada baris yang bisa diubah, sudah hilang dengan sendirinya karena penjualan dan mutasi stok append-only. Sync engine baru sepadan biayanya kalau nanti ada beberapa kasir per toko yang sama-sama mengedit master data.

Produk POS nyata menganggap offline sebagai mode darurat

Semua produk yang punya dokumentasi offline memakai pola yang sama: penyimpanan lokal di terminal ditambah antrean unggah. Loyverse menandai struk offline "Unsynced" dan menyinkronkannya otomatis (Loyverse). Square menyimpan pembayaran offline di app dan memberi batas 72 jam sebelum kedaluwarsa (Square). Shopify menyarankan tersambung lagi dalam 24 jam (Shopify). Toast menunjuk satu perangkat berkabel sebagai local hub yang me-relay data antarperangkat di LAN (Toast). Di sisi open source, uniCenta dan Floreant (Java) memakai Apache Derby tertanam (uniCenta, Floreant). Bundle Windows NexoPOS bahkan memakai SQLite (NexoPOS). Pola "DB tertanam di mesin kasir, DB pusat opsional" sudah terbukti puluhan tahun. Usulan Go + SQLite pada dasarnya versi modern dari pola itu.

Hal paling berguna dari produk-produk ini adalah strategi konfliknya. Tidak ada satu pun yang mendokumentasikan last-write-wins atau CRDT. Mereka menghindari konflik dengan tiga cara. Penjualan dibuat append-only dan idempotent lewat ID dari klien. Server memegang otoritas atas katalog dan stok. Operasi yang berpotensi konflik dimatikan saat offline: Loyverse menonaktifkan refund dan registrasi pelanggan, serta menyembunyikan level stok saat offline (Loyverse), sementara Toast mematikan gift card dan house account (Toast). POS Awesome V15 jadi referensi terbuka paling jelas. Di sana "Request IDs make replays duplicate-safe", submit yang gagal disimpan sebagai Draft, dan validasi stok server tetap berjalan saat sync meskipun penjualan offline tanpa cek stok diizinkan (POS-Awesome-V15).

Ada aturan UX yang dipakai berulang oleh vendor: jangan izinkan logout atau hapus data selama antrean belum kosong. Loyverse memblokir sign out jika masih ada struk unsynced (Loyverse). Square memperingatkan bahwa pembayaran pending "will be permanently lost" jika pengguna logout atau menghapus app (Square). Toast memberi peringatan serupa untuk clear cache (Toast). Dengan SQLite di disk, risiko ini jauh lebih kecil, tapi indikator "N transaksi belum tersinkron" dan blokir untuk tindakan destruktif tetap layak dibuat.

Pasar Indonesia punya basis yang berbeda. Moka, Majoo, Pawoon, dan Qasir mengutamakan Android dengan printer Bluetooth 58 mm. Windows hanya opsi sekunder: Majoo mencantumkan Windows 10 build 17763+ (Majoo FAQ), dan tutorial Qasir hanya membahas printer Bluetooth (Qasir). Klaim "bisa offline" dari Moka dan Pawoon cuma muncul di ulasan pesaing dan listing App Store (HashMicro, App Store Pawoon). Tidak ada dokumentasi teknis sinkronisasi dari vendor Indonesia mana pun, dan tidak ada post-mortem publik dari vendor besar soal transaksi ganda atau stok yang melenceng. Jadi pola di atas disimpulkan dari dokumentasi help center dan README, bukan dari studi kasus internal.

SQLite dengan synchronous=FULL cukup untuk bertahun-tahun

Pedoman resmi SQLite cocok persis dengan kasus ini. Pilih client/server hanya jika data dipisahkan dari aplikasi oleh jaringan, ada banyak penulis bersamaan yang "cannot queue up and take turns", atau ukuran data mendekati terabyte. Selain itu, "SQLite is almost always a better solution". Kalau app server dan DB berada di satu mesin, SQLite tetap layak walaupun pengguna akhirnya mengakses lewat jaringan (sqlite.org/whentouse). HP pemilik tidak pernah menyentuh file DB. HP hanya memanggil HTTP ke server Go. Sebaliknya, PostgreSQL di PC kasir menambah satu service lagi, installer yang bergantung pada EDB (postgresql.org), dan kewajiban upgrade major lewat dump/reload atau pg_upgrade dalam lima tahun (PG versioning). Itu beban operasional yang tidak sepadan untuk toko yang tidak punya orang IT.

Pengaturan yang sering salah adalah durability. SQLite sendiri menyebut synchronous=NORMAL sebagai keseimbangan terbaik di mode WAL, tapi mengakui bahwa transaksi yang sudah commit "might roll back following a power loss" (sqlite.org/pragma). Untuk mesin kasir di wilayah yang sering mati listrik, kehilangan struk terakhir tidak bisa diterima. Pakai synchronous=FULL. Biayanya satu fsync tambahan per commit, dan di kecepatan transaksi kasir itu tidak terasa. Pengaturan lain yang direkomendasikan: journal_mode=WAL, busy_timeout=5000, foreign_keys=ON, satu koneksi penulis (SetMaxOpenConns(1)), dan pool terpisah untuk query dashboard. Satu hal lagi: WAL punya bug korupsi akibat race saat reset WAL yang baru diperbaiki di 3.51.3+ (sqlite.org/wal). Jadi versi SQLite yang dibundel driver ikut menentukan.

Ketiga driver Go sama-sama aktif di 2026, dan pilihannya bergantung pada toolchain, bukan kecepatan:

Pilih modernc sebagai default. GOOS=windows go build menghasilkan satu .exe tanpa toolchain C. FTS5 untuk pencarian nama produk dan JSON1 sudah aktif lewat flag kompilasi di generator-nya. Versi SQLite yang dibundel (3.53.4) juga sudah melewati perbaikan bug WAL tadi. Selisih kecepatan tidak relevan untuk 20 ribu produk. Benchmark independen pada workload "Real" mencatat insert 1.759 ms untuk modernc dibanding 1.586 ms untuk mattn, dan penulisnya sendiri bilang "We cannot declare a clear winner" (go-sqlite-bench). Benchmark itu dijalankan di Linux, bukan Windows.

Untuk tooling, sqlc mendukung SQLite tapi masih Beta (PostgreSQL sudah Stable) (sqlc docs). Ada 64 issue terbuka berlabel sqlite, termasuk rowid yang tidak jalan di tabel FTS5 dan sqlc.slice() yang merusak query (GitHub issues). Pakai sqlc untuk CRUD dan laporan, tapi tulis manual query FTS5 dan query dengan IN dinamis. goose v3.29.0 mendukung SQLite dan Postgres serta migrasi yang di-embed lewat embed.FS (goose), jadi migrasi bisa ikut di dalam .exe dan dijalankan saat service start. Karena dialek SQL SQLite dan Postgres berbeda, taruh domain di belakang interface repository sejak awal agar implementasi Postgres untuk hub cloud bisa ditambahkan tanpa membongkar logika bisnis.

Model datanya yang paling menentukan. sales dan sale_items dibuat immutable dengan key UUIDv7 dari klien. stock_movements append-only, mencatat jual, terima barang, penyesuaian, opname, dan transfer antarcabang, semuanya dengan branch_id. Stok saat ini dihitung dari jumlah semua movement (boleh di-cache di tabel proyeksi). Uang disimpan sebagai rupiah integer, dan koreksi dibuat sebagai baris void atau refund baru. Inventaris sebagai ledger penyesuaian, bukan satu angka, juga direkomendasikan praktisi integrasi POS (Modracx). Dengan model ini, mekanisme sync apa pun, termasuk yang LWW, jadi aman karena insert dengan UUID unik tidak pernah konflik. Oversell saat beberapa terminal offline cukup ditandai untuk ditinjau pemilik, bukan diblokir di kasir.

Printer dan laci lewat Go, bukan lewat browser

Rute cetak yang paling andal adalah byte ESC/POS RAW dari service Go ke Windows spooler: OpenPrinter, lalu StartDocPrinter dengan datatype "RAW", lalu WritePrinter. Cara ini memakai driver bawaan vendor dan tidak perlu menukar driver (alexbrainman/printer). Alternatifnya punya masalah masing-masing. WebUSB masih Experimental dan bukan Baseline (MDN). Di Windows, WebUSB gagal dengan "Access denied" sampai driver printer diganti WinUSB lewat Zadig, langkah yang oleh seorang developer Zebra disebut "not viable for our customer base" (Zebra forum). Penggantian driver itu juga mengeluarkan printer dari spooler Windows. window.print() dengan --kiosk-printing memaksa printer default, tidak bisa mengirim perintah potong kertas atau buka laci, dan dilaporkan pernah rusak di Edge 96 (Koha wiki, churchteams). QZ Tray (v2.3.0, LGPL) berfungsi, tapi menambah aplikasi tray Java yang perannya tumpang-tindih dengan service Go (qzind/tray).

Ekosistem library ESC/POS untuk Go masih tipis. hennedo/escpos punya API rapi dengan lisensi MIT, tapi commit terakhirnya November 2022 dan tidak ada fungsi laci (GitHub). DevLumuz/go-escpos v1.0.2 sudah mencakup winspool dan status DrawerOpen, tapi belum punya importer (pkg.go.dev). alexbrainman/printer tidak berubah sejak 2020. Struk hanya butuh sebagian kecil perintah (ESC @, ESC a, ESC E, GS !, ESC t, GS V, ESC p), jadi byte-builder sendiri sekitar 200 baris plus wrapper winspool lewat golang.org/x/sys/windows lebih aman daripada bergantung pada library yang tidak terawat. Laci dibuka dengan ESC p m t1 t2: m=0 untuk pin 2, m=1 untuk pin 5, dan durasi pulsa t×2 ms. Nilai yang umum adalah 1B 70 00 19 FA (ESC p 0 25 250) (Epson, UMD AN142). Buat pilihan pin bisa dikonfigurasi, dan jangan kirim pulsa berulang karena solenoid laci bisa kepanasan (SambaPOS forum). Satu hal belum terverifikasi: apakah printer 58 mm murah (Xprinter, EPPOS) mendukung pin 5, dan apakah lebar kolom 32/48 untuk 58/80 mm sesuai. Cek manual unit yang dibeli.

Scanner USB HID bekerja sebagai keyboard: kode diketik lalu diakhiri Enter. Di UI, pasang listener keydown global. Burst karakter yang datang dengan jeda di bawah sekitar 20–40 ms dan diakhiri Enter dianggap hasil scan (SO via kiwix). Tambahkan prefix atau suffix yang jarang diketik manusia lewat konfigurasi scanner agar deteksinya pasti (onscan.js). Cara ini sama di Edge, WebView2, maupun Electron karena tidak butuh driver apa pun.

Untuk "jendela" kasir, Edge mode kiosk yang mengarah ke localhost adalah baseline paling ringan. Edge sudah ada di Windows, dan perintahnya cukup msedge.exe --kiosk URL --edge-kiosk-type=fullscreen. Mode kiosk memblokir F11/F12 dan Ctrl+N, tapi tidak mendukung extension, dan --kiosk-idle-timeout-minutes tidak me-restart Edge. Restart otomatis butuh Assigned Access (MS Learn). Kalau ingin aplikasi berjendela sungguhan, pilih Wails v2 (v2.14.0, Agustus 2026) yang tetap Go dan memakai WebView2. Hindari v3 karena masih v3.0.0-beta.29 tanpa tanggal rilis final (wails releases, GitHub API). Tauri v2 (2.12.x) matang (Tauri), tapi lapisan native-nya Rust, sehingga menambah satu bahasa dan toolchain tanpa banyak keuntungan dibanding Wails. Electron 44 jauh lebih berat. Benchmark blog menyebut bundle 85 MB dan idle 168 MB untuk Electron, dibanding 3,2 MB dan 42 MB untuk Tauri, walaupun metodologinya meragukan (Tech Insider). Apa pun shell-nya, UI harus tetap SPA biasa yang disajikan Go lewat HTTP, karena HP pemilik juga memakainya.

Frontend yang direkomendasikan adalah React 19.3 + Vite 8 + TanStack Router + TanStack Query 5 + Tailwind 4.3 + shadcn (CLI v4). Semuanya rilis aktif per Oktober 2026 (react.dev, npm vite, npm @tanstack/react-router). TanStack Router dipilih karena memberi tipe pada params dan search params di mode SPA. React Router v8 (Juni 2026) lebih fokus ke middleware dan prerendering untuk framework mode (changelog), yang tidak dibutuhkan SPA yang di-embed di Go. Kontrak API antara Go dan TypeScript sebaiknya spec-first OpenAPI: oapi-codegen v2.8.0 di sisi Go (dukungan awal OpenAPI 3.1; v2.7.1–2.7.2 menambal celah code injection dari spec berbahaya) (oapi-codegen), dan orval 8.43 untuk hook TanStack Query atau openapi-typescript + openapi-fetch untuk runtime minimal (npm orval). ConnectRPC v2 baru masuk akal kalau nanti ingin streaming penjualan langsung ke dashboard (connect-go). Kalau dukungan 3.1 terasa belum lengkap, tulis spec dalam versi 3.0.3.

Rp0 berlaku untuk hosting, tidak untuk akses jarak jauh

Asumsi "Tailscale gratis" perlu dikoreksi. Paket Personal ($0, 6 user) secara eksplisit "only suitable for non-commercial use", dan paket yang sesuai untuk usaha adalah Standard $8 per user per bulan (tailscale.com/pricing). Secara teknis Tailscale paling nyaman. Ia bisa berjalan unattended sebagai service Windows (KB 1088) dan menyediakan sertifikat Let's Encrypt lewat tailscale cert. Catatannya, sertifikat itu berlaku 90 hari, harus diperpanjang sendiri, dan nama mesin serta nama tailnet muncul di log Certificate Transparency (KB 1153). Jalur Rp0 yang sah adalah Cloudflare Tunnel + Access. cloudflared hanya membuka koneksi keluar, jadi tidak ada port yang perlu dibuka di router toko (Cloudflare), dan paket Zero Trust Free mencakup sampai 50 user (blog Cloudflare). Syaratnya, domain harus terdaftar di Cloudflare sebelum aplikasi bisa dipublikasikan (Cloudflare docs). Quick Tunnel trycloudflare.com tidak bisa jadi jalan pintas karena hanya untuk testing, tanpa jaminan uptime, tanpa SSE, dan hostname-nya berganti setiap kali dibuat (trycloudflare). Angka 50 user gratis berasal dari blog resmi tahun 2020 dan ringkasan pencarian tahun 2026, karena halaman harga terkini gagal dimuat. Cek ulang sebelum dipakai.

Untuk backup, Litestream aktif dirawat (v0.5.17, Agustus 2026) dan menyediakan zip untuk Windows serta panduan service lewat sc.exe (litestream.io). Namun release notes-nya menyebut binary Windows "for convenience… at your own risk", dan platform resminya hanya Linux dan macOS (releases). Belum diverifikasi juga apakah litestream.exe menjalankan protokol Service Control Manager. Kalau tidak, sc.exe create bisa gagal dengan error 1053. LiteFS tidak bisa dipakai karena berbasis FUSE dan masih beta (litefs). Backup utama sebaiknya dikendalikan aplikasi sendiri: service Go menjalankan VACUUM INTO ke file .tmp, lalu rename. Hasilnya snapshot konsisten yang di-fsync ketika sumbernya memakai synchronous FULL, tapi bisa korup kalau prosesnya terputus di tengah, makanya pakai pola tmp-lalu-rename (sqlite.org/lang_vacuum). Jalankan setiap beberapa jam dan saat tutup kasir, simpan juga salinannya ke USB drive, lalu unggah ke Cloudflare R2 free tier: 10 GB-bulan, 1 juta operasi Class A, egress gratis (R2 pricing). Tiga puluh snapshot harian 50 MB baru sekitar 1,5 GB. Litestream bisa ditambahkan belakangan sebagai replikasi best-effort, dengan interval sync yang cukup panjang supaya jumlah PUT tidak mendekati batas Class A.

Ketika cabang kedua datang, hub cloud bisa tetap Rp0. Pilihannya Neon Free (1 GB per proyek, scale-to-zero setelah 5 menit dan tidak bisa dimatikan) (Neon) ditambah API Go di Cloud Run (2 juta request per bulan) (Google Cloud). Hindari dua opsi ini untuk data produksi: Supabase Free dijeda setelah satu minggu tidak aktif (Supabase), dan Postgres gratis Render kedaluwarsa 30 hari setelah dibuat (Render). Fly.io sudah tidak punya free tier untuk organisasi baru (Fly). Oracle Always Free (setara 2 OCPU dan 12 GB di A1) paling murah hati, tapi instance yang dianggap idle selama tujuh hari bisa diambil kembali (Oracle), dan server sync toko kecil gampang masuk kategori idle itu. Kalau siap membayar, VPS lokal mulai sekitar Rp59 ribu per bulan (Biznet Gio NEO Lite XS, dengan harga yang berubah-ubah antarversi halaman) (Biznet Gio) atau Rp116.900 promo untuk Hostinger KVM 1 di Jakarta (Rp193.900 saat perpanjangan) (Hostinger).

Stack final dan jalur ke multi-cabang

Go juga menang dari sisi deployment di Windows. golang.org/x/sys/windows/svc (v0.49.0, Oktober 2026) menyediakan semua yang dibutuhkan untuk Windows service, dan kardianos/service memungkinkan binary memasang dirinya sendiri sebagai service (pkg.go.dev, kardianos/service). .NET 10 sama mampunya di Windows (MS Learn), tapi developernya menguasai Go. Node SEA masih "Active development" dan tidak bisa memuat native addon seperti better-sqlite3 langsung dari bundle (Node docs). Dokumentasi Bun sendiri menyebut binary-nya "way too big" (Bun).

Urutan kerjanya: rilis dulu server lokal dengan skema yang sudah siap hub. Pada tahap ini dashboard HP mengakses PC kasir langsung lewat tunnel. Setelah itu tambahkan relay ke Postgres cloud, supaya dashboard tetap bisa dibuka ketika PC kasir mati, lalu sambungkan cabang berikutnya sebagai spoke dengan pola yang sama. PowerSync baru dipertimbangkan lagi kalau satu toko punya beberapa terminal yang sama-sama mengedit master data.

Kesimpulan

Keputusan teknis paling penting di proyek ini adalah model datanya, bukan pilihan sync engine atau shell desktop. Begitu penjualan dan stok dibuat append-only dengan ID dari klien, pertanyaan "engine mana yang menangani konflik dengan benar" tidak relevan lagi. Itu juga menjelaskan kenapa Square, Toast, dan Loyverse tidak mendokumentasikan algoritma konflik apa pun: mereka mendesain supaya konflik tidak terjadi, lalu mematikan fitur yang tersisa saat offline. Kebutuhan printer USB dan laci uang juga ikut memutuskan arsitektur. Agen lokal wajib ada demi hardware, jadi menaruh data di agen yang sama membuat sistem lebih sederhana, bukan lebih rumit. Satu PC kasir dengan server lokal juga menjadi titik gagal tunggal, sehingga backup terjadwal dan UPS bukan tambahan opsional tapi bagian dari arsitektur.

Ada beberapa ketidakpastian yang perlu diuji langsung di prototipe, tidak bisa diputuskan dari riset ini saja. Pertama, perilaku litestream.exe sebagai service. Kedua, dukungan pin laci dan lebar kolom di printer murah yang benar-benar dibeli. Ketiga, apakah kebijakan WebView2 dan Edge kiosk di Windows 10 milik toko berjalan sesuai dokumentasi. Keempat, apakah free tier Cloudflare Zero Trust masih 50 user. Pasar sync engine sedang berkonsolidasi (Supabase menyerap Turso dan tim Triplit), jadi skema dan event log yang portabel adalah cara termurah untuk tetap bebas memilih nanti. Target Rp0 sendiri sedikit menyesatkan: hosting memang bisa gratis, tapi akses jarak jauh yang sah dan andal tetap butuh biaya kecil, entah satu domain per tahun atau $8 per user per bulan untuk Tailscale. Sebaiknya angka itu dikomunikasikan ke pemilik toko sejak awal.
